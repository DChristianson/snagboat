# Privacy

Snagboat keeps everything it observes on the developer's machine, and there is no telemetry of the extension itself. The one exception is the optional advisor: if you add a hosted provider and approve its payload, a redacted digest of the session you ask about is sent to it (see [The advisor](#the-advisor)).

## What is captured

**Which projects.** The VS Code extension records the projects you open in VS Code. The core service (`snagboat serve`, which VS Code starts) goes further: while it runs, it reads Claude Code's transcripts (`~/.claude/projects`) and Copilot CLI's session logs (`~/.copilot/session-state`) for **every project on this machine**, including ones you've never opened in VS Code, and records them in `~/.snagboat/data`, with your prompts' text unless capture is off for that project. To limit it: `"collect": false` for a project (in `~/.snagboat/config.json` or its `.snagboat.json`), or `"collect.unopened": false` in `config.json`'s defaults to record only projects VS Code knows ([settings](docs/settings.md#outside-vs-code-snagboatconfigjson-and-snagboatjson)), or `snagboat serve --no-collect`.

**Git history.** The core service also reads the git history of the projects it records, read-only (`git log`, `git show`, `git blame`, with git's optional locks off so it never gets in your way), to learn what became of commits made during a session: whether each was kept or reverted after 7 days, how many of the lines it added are still there after 7 and 30 days, and whether it came after the session's tests last passed. It reads only repositories of projects with recorded sessions, about commits that touch files a session's agent edited, and stores only commit ids, counts and times, never code. The core also records the repository itself, in each project's `git.jsonl`: its commits (author and committer names and emails, co-authors, commit subjects, the paths of the files changed and how many lines, never the code, and the rest of each commit message only with `snagboat.captureContent` on, and for `retention.textDays`), its branch names and what became of them, and the checkouts in each working tree, from `git log`, `git for-each-ref` and the reflog, for as long as `retention.rawDays` keeps raw events. It makes no network requests. `snagboat.outcomes.git` (or `"outcomes.git": false` in `config.json` or a project's `.snagboat.json`) turns it off.

**Plans.** The core records each project's plan in its `plan.jsonl`. For a project with [Beads](https://github.com/steveyegge/beads), it runs `bd --readonly export` and `bd --readonly history --events` (or reads what a dev container's exporter wrote to `.snagboat/beads/`): each issue's title, kind, status, priority, labels, parent and dependencies, times, close reason, assignee, owner and creator, and its lifecycle with who did each step (for an update, only which fields changed). The issue's description, design, notes and acceptance criteria are kept only with `snagboat.captureContent` on, and for `retention.textDays`. Without beads, it reads the markdown git tracks under `docs/` (or the project's `plans` setting) and records the checklists and numbered steps it finds, with the time and author (name and email) of the commit that last changed each line. The same `outcomes.git` and `collect` settings turn it off.

[docs/data-sources.md](docs/data-sources.md) compares where this comes from for each place you chat, and what a project's committed files mean for collaborators.

Each observed action becomes one normalized event (see [docs/schema.md](docs/schema.md)). Most fields are structural (kind, status, timestamps, session id, model, token counts), but some carry details of what the agent did:

### Captured text

**`snagboat.captureContent` is on by default.** It stores five kinds of text: your prompts (`promptText`), reply excerpts (`textExcerpt`), session names (`sessionName`), the items of the agent's todo list (`todos.items`, or its tasks' subjects in `taskOp`), and tool calls' commands, search patterns, URLs and descriptions (`toolInput`). How much of a prompt or reply is kept is up to `snagboat.capture.promptChars` (default 2,000 characters) and `snagboat.capture.replyChars` (default 500), each up to 100,000 and settable per folder; a raised cap applies to what's captured from then on, and an event whose text was cut says so (`textTruncated`). Prompts and replies give the Sessions tab and the verbal-hedge heuristic something to show; names make sessions recognizable; todo items are what Navigator's Ahead line shows when a workspace has no Beads. With capture off, a todo list is recorded as counts only, and tasks as ids and statuses. Earlier versions stored no prompt text and had this setting off by default; installs that never changed it start capturing text from this version on.

Text is protected three ways instead of by an opt-in:

- **Redaction.** Before anything is stored, common secret formats are replaced with a `[redacted …]` marker: private key blocks, AWS keys, GitHub, Anthropic, OpenAI, Stripe, Slack, and Google tokens, JWTs, bearer tokens, passwords in URLs, and `password=`/`token=`/`api_key=`-style values that look like secrets. It's a backstop for the common cases, not a guarantee: a secret in an unrecognized format is stored as is.
- **Shorter retention.** Prompts, reply excerpts, todo items and tool inputs' text are kept for `snagboat.retention.textDays` (default 30 days, the same as Claude Code keeps its own transcripts), then removed from their events, which stay for `rawDays`. So are commit message bodies (in `git.jsonl`, by the commit's time) and plan items' text (in `plan.jsonl`, by the item's last update); the commits and items stay, with their subjects and titles. Session names stay with their session's events.
- **Removal.** `Snagboat: Remove Captured Text` removes every stored prompt, reply excerpt, todo item and tool input's text from the workspace's events now (a todo list's counts, a task's id and status, and a tool call's path and refs stay), and every commit message body and plan item's text from the workspace's `git.jsonl` and `plan.jsonl` (subjects, titles, co-authors and the rest stay), and can turn capture off at the same time. It removes text from this workspace's store only: other workspaces, including other worktrees of the same repository, which keep their own copies of its commits, keep theirs until they're cleared from their own window or `textDays` removes it. The files are rewritten, so the text is gone from disk; a commit or item that later changes, with capture on, is stored whole again.

The text is stored **in the same event logs as everything else**, not in a separate store (commit bodies and plan text in the project's `git.jsonl` and `plan.jsonl`). Turning the setting off stops new capture of all five, and of commit bodies and plan text; text already stored stays until text retention removes it or you run Remove Captured Text. Token tracking and the behavioral heuristics never require it.

The same text is already on disk in the agents' own logs: Claude Code keeps full prompts in its transcripts, and Copilot in its session logs. Snagboat's copy adds a second location (`~/.snagboat/data`, and whatever backs it up) for up to `textDays`.

Note that Copilot's own `github.copilot.chat.otel.captureContent` makes Copilot send full prompts, replies, and tool results to Snagboat's local receiver. Snagboat keeps only the truncated reply text and discards the rest without logging it.

## The advisor

Advisors are models you configure (`snagboat.advisors`, or the short form `snagboat.advisor.providers`), each offering some of three abilities, and each ability names the advisor it uses (`snagboat.advisor.defaults`) unless you pick another. How to set one up is in [advisor models](docs/advisor-models.md). What is sent depends on the ability:

- **Summarize a session** (**Explain**, in the Sessions tab, on a notification, or **Snagboat: Explain Session...**) sends one **session digest** per request.
- **Report on a goal** (a goal advisor's performance report, asked by the core of the local model its `persona.md` names) sends no session digest: the advisor's goal and measures, the period's measure values against its last report (overall and per workspace, with workspace folder names only when paths aren't hashed), the tunable thresholds and their values, the ids and titles of your saved rules, the running experiments, the last round of proposals with what you did with them and your notes, and the changes you discarded.
- **Session headlines** (`snagboat.advisor.headlines`, off by default) send each ended session's digest to the `summarize-session` advisor once, quietly, after it has been idle past the `stalled` window, but only to an advisor whose current payload you've already approved; it never asks while you work.
- **Set up an advisor** (a conversation on the advisor UI's **+** page, asked by the core of local advisors only) sends what you type in that conversation, the model's earlier answers in it, and Snagboat's lists to choose from: measure ids and labels, the ids and titles of the heuristics and saved rules, and the advisor names already taken. Nothing from your sessions. It has its own approval, apart from the advisor's other abilities.

By default every ability uses a local model (Ollama on `localhost`), and nothing leaves the machine. An advisor is treated as local only if its address is a loopback address (`localhost`, `127.0.0.1`, `::1`), whatever its name. Any other advisor is hosted: it must use https, needs your API key, and is audited. Sending rules (`send`) are set per advisor, and can be set per ability, so an advisor can get prompts when it explains a session and none for another ability. Widening what an ability may receive changes what you approve, so you see the payload again. An advisor's own prompts (its goal and voice, and per-ability instructions) change what it's asked, never what data is sent: Snagboat appends its data-handling rules after them, and the approval document shows the whole system prompt.

Digests are built from the stored events for one request and contain:

- **Always:** session and turn ids, times, counts of turns, model calls, and tool calls; token counts and context peaks; tool categories, failures, compactions; findings, with summaries redacted the same way as targets.
- **Shell commands:** only their category and command name (`tests-builds: npm`). Never arguments, environment variables, or the rest of the line.
- **File paths:** relative to the workspace, or, when outside it or when `send.paths` is `hashed`, a short hash that keeps the extension (`file-3dbaa72f.md`).
- **Prompt text:** for local advisors by default; for hosted ones only with `send.prompts`, per ability. Capped at 1,000 characters per turn, after the redaction applied at capture.
- **Each turn's model** (the main agent's model with the most calls), with the other counts.
- **Session names:** local by default; hosted only with `send.sessionNames`.
- **Reply excerpts:** never, unless a provider has `send.replies`.

The request carries a fixed instruction and the data, and offers the model no tools. What a model sends back is only ever shown as model output; a proposed rule or category is checked like one you'd write and saved only if you accept it. Before a provider's first request, and whenever its address or sending rules change, Snagboat shows the exact payload and asks. **Snagboat: Preview Advisor Digest...** shows a digest any time.

## Where data is stored

The files below live in one per-user store, written by the core service: a workspace's `events/`, `aggregates/`, `checkpoints/` and `finding-responses.jsonl` in `~/.snagboat/data/workspaces/<workspace>/` (with a `workspace.json` naming the folder), `rules.json` in `~/.snagboat/`, and `context-limits.json`, `advisor-audit.jsonl` and `copilot-structure/` in `~/.snagboat/data/`. Each event there also records its workspace's folder path. VS Code keeps none of it in its own storage. Earlier versions kept each window's data under the extension's per-workspace storage folder; a window's start, or running `snagboat migrate`, **copies** that data into the per-user store and leaves the original where it was (Snagboat no longer writes or reads it, except the CLI's `--store vscode` and `migrate`; delete it by hand if you like); `~/.snagboat/data/migrated/` records what was copied. Each copy is subject to the same retention, applied by the core service. To remove the per-user store, uninstall Snagboat (or stop the core with `snagboat core stop`) and delete `~/.snagboat/data` (and `~/.snagboat/rules.json`).

## Exports

Nothing leaves your machine unless you export it. `snagboat export` (and **Snagboat: Export Project...**) writes one project's records from the store to a folder you choose, for you to share or load into Factory Clock. It reads only the store, never git, bd or transcripts, and makes no network calls. In the store it writes only its own state, in the project's folder: your decisions, and a review file while values are undecided. The design is in [the export design](docs/design/export.md#the-privacy-filter); in short:

**What an export contains:** the project's sessions (counts, tokens, models, names, where they ran, linked branches, commits and plan items), their events (prompts, reply excerpts, tool names, categories, statuses, timings and the inputs the store kept: commands, paths, search patterns, URLs), finding episodes and your responses, commits (subjects, bodies, changed files and line counts), branches, checkouts, plan items (titles, text, status, lifecycle) and the links between them, and a `manifest.json` with counts and what the filter rewrote and kept. Stored events' `workspace` and `raw` (which name transcript files) are never exported, and times are in UTC, without git's timezone offsets. `--text none` drops all text and keeps the structure.

**The privacy filter** finds values that might hurt you or your project if they left your machine, and asks you about each before anything is written: it's your data and your decision, and the filter is there to support it, not to promise it found everything. Its rules, generated from the code:

A rule set to `review` asks you about each value it finds; `rewrite` and `keep` decide for you unless you decided a value yourself; `off` doesn't run. Set them in `export.rules` in `~/.snagboat/config.json` (a project's `.snagboat.json` can't), or for one run with `--rule`, `--rewrite-all` or `--no-filter`.

**The review file** holds the values the filter found, with snippets of where they appear, so it's kept in the store (`~/.snagboat/data/workspaces/<key>/export-review.json`), never in the project or beside the export. Your decisions are kept beside it, keyed by a hash of each rule and value, never the value, and later exports ask only about new values. Placeholders (`[person-N]`, `[email-N]`, `[commit-N]`) are numbered per export, so two exports don't share them.

**Where the export goes:** never inside the project or its worktrees, where it could be committed, except under the project's `.snagboat/` folder, where the export writes a `.gitignore` for it. Never inside `~/.snagboat/data`.

## Retention

On activation, hourly, and whenever the retention settings change:

- raw daily files older than `rawDays` are rolled up into `aggregates/<date>.json` and deleted;
- aggregates older than `aggregateDays` are removed;
- raw days older than `textDays` (capped at `rawDays`) have their prompt text, reply excerpts, todo items' and tool inputs' text removed in place: the events stay, without the text. Commit bodies and plan items' text older than `textDays` go from `git.jsonl` and `plan.jsonl` the same way.

Events are filed under the day they happened, so history caught up from an old transcript is retained by its own date: anything older than `rawDays` goes straight into that day's aggregate, anything older than `aggregateDays` isn't stored, and text older than `textDays` is never written.

The core service applies the same retention, every 6 hours and when it starts, to the workspaces it records that no VS Code window has open, using each workspace's own settings (`~/.snagboat/config.json`, `.snagboat.json`). A workspace whose window writes it itself (when the core couldn't start) is the window's to prune.

**Still one clock:** other fields, including command-string `target`s and file paths, live as long as their event (`rawDays`). Whether those need a shorter retention of their own is still open.

## User controls

- `Snagboat: Clear Event Log` (`snagboat.clearLog`) deletes all raw logs and daily aggregates after a confirmation prompt. Adapter checkpoints are kept so already-seen transcript history is not re-imported.
- `Snagboat: Remove Captured Text` (`snagboat.removeCapturedText`) removes every prompt, reply excerpt, todo item and tool input's text stored for the workspace after a confirmation prompt, keeping the events, and every commit message body and plan item's text in its store, keeping the commits and items, and can turn capture off too. Other workspaces (other worktrees of the repository included) keep theirs.
- `Snagboat: Remove Claude Code Hooks from Project...` (`snagboat.removeClaudeHooks`) removes Snagboat's hook entries from a folder's `.claude/settings.json` and turns off `snagboat.claudeCode.configureHooks` for it, so they aren't added back.
- `snagboat.captureContent` (on by default) turns all text capture on or off; `snagboat.retention.textDays` sets how long prompts and replies are kept. The detail view shows whether capture is on and for how long text is kept.

## The advisor UI

The core serves the advisor UI at `http://127.0.0.1:<port>/ui/`, on this machine only. It answers only requests addressed to `127.0.0.1` or `localhost` (so a web page that renames itself to look local can't reach it), plus, in a remote VS Code window, the forwarded address VS Code gives it, and the page is sent with a policy that lets it load only its own files and talk only to the core. `snagboat open` or **Snagboat: Open Advisor UI** gives the browser a one-time code in the link's fragment, which browsers never send to a server; the page swaps it once for a read-only key, kept in that tab's session storage; it ends after 12 hours unused, when the core stops, or when a 21st is opened (the oldest ends). The workspace shown is kept there too, not in the address, so your project paths stay out of browser history. That key can read every workspace's sessions (including the prompt text and reply excerpts kept when `snagboat.captureContent` is on, which the session page shows, as VS Code's Sessions tab does), findings, outcomes and advisors' measures, and can send back only these: **Useful**, **Acknowledge**, **Mute** or **Unmute** on a finding, which the core keeps for every front door (the page, VS Code, the Claude Code plugin); a new advisor from the **+** form, written as a new `~/.snagboat/advisors/<id>/persona.md` (owner-only), never over one that exists; a setup conversation on that page (your turns, which the core sends to the local model you pick, and accepting, revising or discarding its proposed advisor); and what you do on the Suggestions page: accepting or removing a saved rule (`~/.snagboat/rules.json`), applying a suggested threshold (your user settings in `~/.snagboat/config.json`), and dismissing a suggestion (`~/.snagboat/suggestions.json`). It can't write events, change other settings, mint keys or stop the core. Discovery runs in the core over the workspace's own history and sends nothing anywhere. **Ask the advisor** on that page sends a digest to a model, but the core asks only advisors on this machine (a loopback address, such as Ollama), from your user settings, never a project's or a `.snagboat.json`; it holds no API keys, and hosted advisors stay in VS Code. The first request to an advisor, and the first after its address or sending rules change, waits until you've read the exact payload in the page and chosen **Send**; that approval is kept in `~/.snagboat/advisor-approvals.json` (owner-only), shared with VS Code, and a request nobody answers isn't sent.

For Navigator's card, the core reads the work ahead from a workspace's Beads issues when it has a `.beads` folder: it runs `bd --readonly --sandbox` (`ready`, `blocked`, `list`) there, which can't change your issues or push them anywhere, and shows issue ids and titles on the page. Without Beads, it shows the todo list the agent kept in the workspace's most recent session (a live one first) from the events already recorded: the items' text when it was captured, otherwise only how many are done and in progress. The page loads no fonts, scripts or images from anywhere else.

## The Claude Code plugin

The plugin (preview, `plugins/snagboat`) records what VS Code's Claude Code hooks record, through the same forwarder: a tool's name, its target (a file path or command line) and whether it succeeded, turn ends, and for permission prompts only the tool's name. Its MCP tools let the agent in a session read, from the core on `127.0.0.1`, this workspace's findings, session summaries (with a session's name when one was recorded), outcomes and advisors' measures; they never return prompts or replies, and can't respond to findings or change anything. Its status line reads the same core and prints counts only. Outside Claude Code's own folders the plugin writes two files: `~/.snagboat/bin/snagboat`, a short script pointing at the plugin's copy of the CLI, and, only if it's missing, `~/.snagboat/bin/snagboat-hook`, the hook forwarder VS Code installs there, so a project's committed VS Code hook entry works on a machine without VS Code. Changing your status line edits `~/.claude/settings.json` only after you agree to the change Claude shows you.

## Design guardrails

- Logs stay local. Any future sharing or sync feature must be a separate, clearly labeled opt-in.
- The advisor sees only digests built for one request, under its provider's sending rules, after you've seen the payload. Local is the default; hosted providers are opt-in, use https, and are audited. A model gets no tools and no standing access to the log.
- Adapters prefer pointers back to source data (`raw.ref`) over copying payloads into events.
- Heuristics and UI must work without captured text (`promptText`, `textExcerpt`, `sessionName`).
- Token tracking must not require content capture.
