# Changelog

## Unreleased

- **Requirements:** VS Code 1.145 or later (was 1.119), and Node 24 for the `snagboat` CLI.
- **Windows:** Claude Code hooks work on Windows, through Git Bash, which Claude Code itself requires there. Not yet tried on a real Windows machine.
- **Rules:** heuristics written as JSON in `snagboat.rules`, which run alongside the built-ins with the same findings, past findings, acknowledge, and mute. **Shell sub-categories** in `snagboat.toolCategories` split "Shell command" by command prefix. Both are groundwork for heuristics discovered from your own history.
- **Suggestions** tab (**Snagboat: Discover Heuristics**): heuristics suggested from what's unusual in this workspace's last 30 days. You get candidate rules scored by replaying your history, built-in thresholds compared with your own percentiles, and command families that could split "Shell command". Accept, adjust, or dismiss each, and remove saved rules there too.
- **Explain** (optional): ask a model you choose about a session, a turn, or a finding. Local by default (Ollama or any OpenAI-compatible server on this machine). Hosted providers need your key, use https, and are audited. The model sees only a redacted digest, which you approve before the first request. **Snagboat: Preview Advisor Digest...** shows exactly what would be sent.
- **Ask the advisor** in the Suggestions tab: a model you choose names discovery's candidates, proposes up to three rules, and groups your shell commands into categories. Everything it returns is validated, scored by replay, and saved only if you accept.
- **Notifications** (opt-in, `snagboat.nudges.notify`): be told when a finding appears, at most one per turn, with Show in Session, Explain, Acknowledge, and Mute. `runaway-turn` and `context-pressure` warn early, at 80% of their thresholds, and rules can too (`earlyWarning`). `snagboat.nudges.advisor` adds the advisor's one-line suggestion to the tooltip.
- **Snagboat: Write Review**: a weekly Markdown review of this workspace covering what it cost, which heuristics fired and how you responded (acknowledgements and mutes are now recorded), rules to retire or add, and checks on how findings were shown in the status bar. **Ask the Advisor** afterwards adds a model's judgment and suggested changes, and `snagboat.advisor.weeklyReview` writes it weekly.
- **Installed advisors** (`snagboat.advisors`): several advisors, each a model with the abilities it offers (summarize a session, summarize the week, propose heuristics, propose nudges) and its own sending rules per ability; `snagboat.advisor.defaults` picks the one each ability uses, and **Ask another advisor** (Suggestions tab, review notification, **Snagboat: Explain Session with Advisor...**) offers the rest. `snagboat.advisor.providers` keeps working as the short form. The review's advisor part is now two sections, a summary of the week and a review of how findings were shown. The `explainProvider`, `proposeProvider`, `reviewProvider`, and `nudgeProvider` settings are deprecated in favour of `defaults`, and still read.
- **Prompts per advisor:** each advisor can have its own goal and voice (`persona`, `personaFile`, or `~/.snagboat/advisors/<id>/persona.md`) and its own instruction per ability (`prompt`, or `<ability>.md` in that folder), so two local advisors on one model can watch for different things in different voices. Snagboat always appends its data-handling rules and the answer's shape. **Snagboat: Write Default Advisor Prompts...** writes the defaults to edit from, and `npm run eval:advisor -- --advisor a,b` compares advisors from your settings on the same sessions.
- **Prompt text in every ability:** the advisor's instructions now treat each turn's prompt as what the turn was for, and the week's summary gets the first prompt of each costliest session when the advisor's rules allow prompts (never in the review file itself). The digest also carries each turn's model. `npm run eval:advisor -- --prompts both` compares answers with and without prompts.
- **Session headlines** (`snagboat.advisor.headlines`, off by default): one line per ended session from the advisor, under its name in the session list and in the open session's summary line, asked quietly one session at a time.
- **Tactics**: ask the advisor whether the models used fit each turn and whether a different way of prompting would have cost less, on a session in the Sessions tab, with **Snagboat: Propose Tactics for Session...**, and as a third section of the review (the two costliest sessions). `snagboat.advisor.modelTiers` tells it your own ranking of models.
- **Ask the advisor** also sees how your current heuristics and rules did (episodes, acknowledged, expired, muted) and the built-in thresholds against your history, and can propose retiring a rule or changing a threshold; each is a click to act on in the Suggestions tab, and nothing changes by itself.
- **Snagboat: Relabel Shell Calls** gives past shell calls the shell categories in use; Snagboat offers it whenever they change.
- **Snagboat: Export Rules...** and **Snagboat: Import Rules...** move saved rules between machines; imports are replayed over your history before you pick them. See [heuristics.md](https://github.com/DChristianson/snagboat/blob/main/docs/heuristics.md#rules).
- **Explore** tab (experimental): load up to eight sessions from any days and move through a carousel of visualizers that each draw the same sessions their own way: the Sessions tab's turn tree (several sessions as a forest under one root) and context timeline (one per session), plus **session strips** (one row per session over clock time, with idle gaps), **cost per prompt** (one column per turn, stacked by agent or by tool category, sessions side by side), and **context fill** (context size by call index, one line per session). Also a **sequence diagram** (who sent what to whom, in order, with repeated tool calls folded and inferred delegations drawn dashed), an **event graph** (one row per turn, with observed order drawn solid and inferred links dashed), an **actor graph** (you, agents, subagents, models, and tool categories joined by typed edges sized by how often they interacted), and **prompt terms** (the words in your prompts as a co-occurrence graph, from word counts rather than a model, leading back to the prompts behind each word). Also a **Gantt and waterfall** view (rows for you, each agent, and each tool category over clock time, or one row per turn that opens on its own time axis). A **treemap** of tokens (by session, turn, and tool category, or by tool category across sessions). A **heatmap** (tokens by session and hour, tool calls by session and category, or findings by heuristic and day). A **tool-call ribbon** (which tool category followed which within turns, leading back to the turns behind each step). And a **week in one picture** (seven days as rings around a 24-hour clock, with tokens by hour and findings). Also a **histogram** of per-call and per-turn measurements. A **box and violin** view of how measurements vary between sessions. A **ridgeline** of per-call measurements by session or model. A **scatter plot** of turns, length against what they used. A **bubble chart** of sessions by span, tokens, tool calls, and findings. A **sunburst** of the turn tree. A **calendar heatmap** of the loaded sessions by day. A **radar** of session profiles. **Parallel coordinates** over turns. A **streamgraph** of activity over time. A **Sankey** of tokens from sessions through agents to models. An **adjacency matrix** of who acted on whom. And a **swimlane** of who had the ball, in order. A puck, which you can drag to any corner and expand from a small circle to a rounded panel, names the current visualizer, shows its tags, and filters the carousel by them; a turn selected in one is selected in the others. The Sessions tab's turn tree and context timeline are now drawn through the same modules, with no change intended to how they look or behave.
- **Hero views** in the Explore tab, each with its own look: **Living Network**, **Session Fingerprint**, **Conversation Landscape**, **Terminal Board**, and **Factory Clock**. They share a replay clock, which can fit a session's whole span into 60, 30, or 10 seconds and loop.
- **Web demo**: the Explore tab as a page on GitHub Pages (<https://dchristianson.github.io/snagboat/>), over example sessions, or over your own daily files, read in the browser and sent nowhere. **Snagboat: Reveal Event Log Folder** shows the folder those files are in. See [PRIVACY.md](https://github.com/DChristianson/snagboat/blob/main/PRIVACY.md#the-web-demo).
- **Privacy:** the extension no longer exposes its event store, findings, and sessions to other extensions; that API now exists only in test runs.
- **`snagboat` CLI** (early): reads the event logs from a terminal or an agent, without VS Code running. `snagboat sessions` lists the sessions in the workspace containing the current folder (`--all` for every workspace), `session <id>` shows one session's summary, and `stores` shows where the logs are. Every command prints JSON with `--json`. `npm run build` builds it as `dist/snagboat.js`. See the [README](https://github.com/DChristianson/snagboat/blob/main/README.md#command-line-early).
- **Per-user store** (preview, `snagboat.storage.perUserStore`, off by default): keep every workspace's data in `~/.snagboat/data`, one folder per workspace, instead of VS Code's storage for each window, so the `snagboat` CLI and, later, other tools read one place. Turning it on copies the window's existing data there, and nothing is moved or deleted, so turning it off goes back to the old storage as it was. `snagboat migrate` copies every store at once (`--dry-run` to count first, `--verify` to check the result against a saved session list), and `--store user` reads the copy. Events in the per-user store record their workspace (event schema version 2).
- **Core service** (preview): `snagboat serve` runs one local service per user over the per-user store, on `127.0.0.1` only, with a token in `~/.snagboat/core.json`; `snagboat core start|status|stop` manages it in the background, and it stops after 30 idle minutes. Tokens are per workspace, so a client sees only its own workspace's sessions; the admin token in `core.json` reads all of them. Claude Code hooks for a project with no VS Code window open now go to the core, if one runs, instead of being dropped; it records them for the workspace containing the project, and only for workspaces it already knows. Once a core has run, hooks that find no core are kept (owner-only) until it next starts. With `snagboat.storage.perUserStore` on, VS Code starts it and each window becomes its client (below).
- **The core collects** (preview): while `snagboat serve` runs, it reads Claude Code's transcripts for **every project on this machine**, not only ones open in VS Code, files each under the workspace that contains it (or its repository), and applies retention to the workspaces it owns. `"collect": false` for a project, `"collect.unopened": false` in `~/.snagboat/config.json`, or `--no-collect` limits it. Hooks for projects no window knows are now recorded too, under the same rules.
- **Outcomes** (event schema version 3): Snagboat records how work went as `outcome` events in the event log, starting with **tests going green** (a test or build that passes after failing in the same session) and **how you met each finding**. Findings and notifications have a new **Useful** button (it also acknowledges the finding); when a finding clears, Snagboat records whether you marked it useful, muted it, acknowledged it, or let it pass. Outcomes aren't counted as activity. They're the first of the measures the default advisors will use (RFC step 4). Claude Code's failed tool calls are now recorded as they happen: Snagboat also registers its `PostToolUseFailure` hook (failed calls, such as a test command exiting non-zero, never reached `PostToolUse`), and adds it to each project's `.claude/settings.json` on the next activation.
- **Heuristics run in the core** (preview): with `snagboat.storage.perUserStore` on, the core works out each workspace's findings and early warnings, with that workspace's own rules and thresholds (`~/.snagboat/rules.json`, and `config.json` as synced from VS Code), so every window on a workspace shows the same ones. Windows still show them in the status bar and as notifications, and changing a rule or threshold applies right away. `snagboat findings` prints the current workspace's findings from the running core. Tool categories used by the core are your user-level ones, not a project's own.
- **The core reads Copilot CLI sessions** (preview): as for Claude Code, the core reads Copilot CLI's session logs (agent mode) for every project on this machine and files each session under its workspace, with the same limits (`collect`, `collect.unopened`, `--no-collect`). A window that's the core's client no longer reads them itself. Copilot's OpenTelemetry export (editor features) still goes to a window, since its spans don't say which workspace they're from.
- **The extension is the core's client** (preview): with `snagboat.storage.perUserStore` on, VS Code starts the core service, which then records Claude Code sessions in every project on this machine (see above for limiting it). Each window follows its own workspace on the core's live feed, with a token for that workspace only, and sends the core what only it sees (edits, and Copilot's OpenTelemetry export). Several windows on one workspace now show the same data. Backfill, relabelling, removing captured text and clearing the log pause the core's writes to that workspace while they run. A saved multi-root workspace (`.code-workspace`) gets the sessions in each of its folders. Changing retention settings applies them right away. `snagboat core stop` stops the core for good: open windows wait for another to start rather than starting one. If the core can't start, or an older one is running, the window writes its own folder as before. The extension package now includes the CLI (`dist/snagboat.js`), which it runs as the core.
- **Settings outside VS Code** (with the per-user store on): `~/.snagboat/config.json` holds your defaults and per-project settings, copied from VS Code's when they change, and a project can commit `.snagboat.json` with team settings such as thresholds and rules; it can only make privacy settings more private. `snagboat config` shows what applies where. See [settings](https://github.com/DChristianson/snagboat/blob/main/docs/settings.md#outside-vs-code-snagboatconfigjson-and-snagboatjson).
- The `snagboat` CLI also finds stores under VS Code's server (`~/.vscode-server/data/User`, and the Insiders, VSCodium, Cursor and Windsurf servers), where a dev container or Remote-SSH window keeps them; `stores` labels them `Code (server)`. The server doesn't record which workspace a store belongs to, so each window now writes it in its storage folder (`snagboat-workspace.json`): the CLI matches those stores to the current folder and `migrate` copies them. A store from before that gets it the next time its folder is opened; until then, read it with `--all`.

## 0.0.2

**Text capture is now on by default.** Snagboat stores your prompts (up to 2,000 characters), agent reply excerpts (up to 500), and session names, so the Sessions tab can show what you asked and `verbal-hedge` has replies to read. If you installed 0.0.1 and never changed `snagboat.captureContent`, capture starts with this version. Common secret formats are redacted before anything is stored, prompts and replies are kept for 30 days (`snagboat.retention.textDays`), and **Snagboat: Remove Captured Text** deletes what's stored and can turn capture off. Nothing leaves your machine. See [PRIVACY.md](https://github.com/DChristianson/snagboat/blob/main/PRIVACY.md#captured-text).

- **Session names** in the session list, breadcrumb, and Overview: Claude Code's generated title, or Copilot's session name.
- **Copilot Agent reply excerpts**, so `verbal-hedge` works for Copilot agent sessions too.
- **Workspace folders added to an open window** get Claude Code hooks right away, without a reload.
- **Snagboat: Remove Claude Code Hooks from Project...** removes Snagboat's entries from a folder's `.claude/settings.json` and stops adding them there (`snagboat.claudeCode.configureHooks`, new, on by default).
- **Fix:** a Copilot agent session could show as a Claude Code session, with its tool calls counted twice: Copilot runs the hooks in `.claude/settings.json`, Snagboat's included. Those hooks are now ignored for Copilot sessions, and **Snagboat: Backfill Sessions from Transcripts...** removes ones already logged.
- **Faster startup:** the event log is read once on activation instead of about four times.
- **Housekeeping:** checkpoint entries for transcripts and session logs that have since been deleted are dropped.

## 0.0.1

First release. Among what it included:

- **Per-window hook routing:** each VS Code window listens on its own port with an auth token, and one hook script sends each Claude Code hook to the window whose workspace holds the project.
- **Sessions tab:** each session's turn tree and context timeline, with prompts, turns, compactions, subagents (their tokens counted too), and context size per call; turn-based heuristics calibrated by replaying real transcripts, and past findings.
- **Snagboat: Backfill Sessions from Transcripts...** rewrites older days from the session logs they came from, so history logged by older builds gets turns and tool calls.
